# 2026-09-26

## 背景

用户时间紧，三个进程分别在 GPU 0/1/2 上跑 sweep：

- GPU=1 `LAYER_SET=encoder`，GPU=0 `LAYER_SET=head`，GPU=2 `INCLUDE_BASELINE=1 LAYER_SET=all`
- 诉求：GPU=2 那轮**跑完 baseline 就杀掉**，不要 proj 数据；问三轮合并后能否拿到
  "除 proj 外的全部指标"。

## 关键事实：`LAYER_SET=all` 的 job 顺序

`run_nmf_zkp_pdb_sweep.sh` 里 `JOBS` 是**顺序执行**的，构建顺序为：

1. `baseline`（若 `INCLUDE_BASELINE=1`，先 append）
2. encoder 6 个 → 3. proj 6 个 → 4. head 2 个

所以 **baseline 是第一个 job**。杀掉之后那轮的 `train/` 里只剩 `baseline`
（外加可能第一个后续 job 的残骸）。结论：三轮合并 = baseline（来自 all 轮）
+ 6 encoder（来自 GPU=1）+ 2 head（来自 GPU=0）= **9 个 setting，正好没有 proj**，
并且能产出基线配对 delta（这是单独跑 encoder/head 得不到的）。

## 修的 bug：`merge_sweep_reports.sh` 的"按文件去重"是假的

原实现按**文件路径**判断是否已存在，但 tag 内部的运行目录带时间戳
（`train/<tag>/<stamp>_JOB_default/...`），两个来源的时间戳不同 → 永不冲突 →
两份都被拷进合并目录；随后 `summarize_nmf_zkp_pdb_sweep.py::find_validation_csv`
的 `sorted(...)[-1]` 取的是**排序最后**的那份 = **启动更晚的**那份，与命令行给的
优先级无关。危险场景：某轮被 kill，留下半截 tag，会**盖掉**另一轮里同名的完整结果。

改为**按 tag 选来源目录**：有 validation CSV 的（跑完的）优先于没有的；打平则
取命令行更靠前的目录（`--discover` 时是最新的）。另加：

- `--drop-incomplete`：干脆不收没有 validation CSV 的 tag（正是"不要 proj 残骸"的用法）
- `--exclude A,B`：支持 glob（如 `--exclude 'transition_*'`）

## 验证方式（合成 sweep，无需 GPU）

造三份假目录：A=encoder 完整、B=head 完整、C=baseline 完整 + `process_s_init`
半截（无 val CSV，时间戳更晚）+ `process_pll` 半截。实测：

- A 的完整 `process_s_init`(07-10) 胜出，C 的残骸(08-05) 未混入 ✅（修前会混入）
- `--drop-incomplete` → 9 个 tag，`paper_metrics.md` 里 `process_pll` 计数 0 ✅
- `paper_summary.md` 有 9 行 + baseline 配对 delta；`process_pll` 落在 Skipped ✅
- `--discover`（最新在前）下完整版仍胜出 ✅；`--exclude 'transition_*'` → 7 个 tag ✅

## 杀进程的正确姿势

等 `$SWEEP/baseline.exit_code` 出现（或终端里看到 `END baseline exit=0`），然后在
**前台那个终端里 Ctrl-C**（SIGINT 发给整个前台进程组，bash+tee+python 一起停）。
若用 `&`/nohup 启动，则用子进程 argv 里的 `paths.log_dir=$SWEEP` 定位父 bash：

```bash
ps -eo pid,ppid,args | awk -v d="$SWEEP" '/train_lora\.py/ && index($0,d) {print $2; exit}'
```

（注意：三个 sweep 的 bash 命令行**完全一样**，`LAYER_SET` 是环境变量不在 argv 里，
所以不能靠 `pgrep -f` 区分；只有子 python 的 `paths.log_dir=` 能区分。）

## "NMF job 参数量少 → 训练会快多少？"（结论：不会快，最多 ~1.5×）

已核实的事实链：

- `train_lora.py:168` 在注入前对**整个基座**做
  `for p in nmf_root_model.parameters(): p.requires_grad = False`，再以
  `freeze_all=False` 只让 NMF 因子可训练 → **NMF job 冻结全部 168M 参数**；
  baseline（`nmf_zkp_pdb`）**没有任何 `parameter_freezing_config`** → 全量微调。
- 因此逐 step 只有"**dW**"这部分能省（`requires_grad=False` 时 addmm 的
  grad_weight 不计算），forward 与 dX 路径完全相同，dataloader 也相同。
- 反向 ≈ 2F（dX + dW），省掉 dW 后 ≈ 1F → **理论上限 3F→2F = 1.5×**；
  但 RFD3 里 attention/softmax/距离/索引类算子本来就没有 dW，GEMM 占比可能只有
  50–70% → **实际约 1.15–1.25×**。若 `timings/train_loader_next` 与
  `forward_loss_backward` 同量级，则是 dataloader bound，冻结**完全不会**变快。
- 次要项（都靠 `requires_grad` 门控，baseline 独有）：168M 的梯度写入（672MB）、
  AdamW m/v（各 672MB）、`clip_gradients` 求范数、`zero_grad`、
  **`EMA.update()` 每 step 一次**（`fabric.py:785`；`EMA.update` 内部
  `if param.requires_grad` 才 lerp，所以 NMF job 跳过 168M 的 lerp）。
- 所以"6 倍"来自**6 个 encoder job 串行**，不是单步慢 6 倍；encoder 这一族
  ≈ baseline 墙钟的 **5–6 倍**。

**测量手段**：
1. 现成的——`<tag>.run.log` 里 `train_logging` 每个 epoch 打印
   `Elapsed Time (s)` / `Mean Time per Batch (s)`（`train_logging.py:268`，含 dataloader 等待）。
2. 精确归因——`TIMING=1`（本轮新增）注入 `TimingCallback`，把
   `timings/forward_loss_backward`、`timings/optimizer_step`、
   `timings/train_loader_next`、`timings/train_step` 写进 metrics.csv 并定期打印表格。
   已验证：hydra 能解析该 override；钩子链能产出全部 5 个键
   （沙箱里用桩模块跑通，见 `/home/zzj/.workbuddy/tmp/wb_tmp/audit_timing.py`）。

## 产物粒度：逐 job 立刻有，sweep 级汇总只在全部 job 跑完后

`run_one` 是串行循环，**每个 job 结束就立刻产出**自己的全套文件（不用等整个 family）：

- `<SWEEP>/<tag>.run.log`：`tee` 实时写，含每 epoch 的 `Epoch N Summary`
  （`Mean Time per Batch (s)`）与 holdout 输出
- `<SWEEP>/train/<tag>/<stamp>_JOB_default/lightning_logs/version_0/metrics.csv`：训练曲线
- `<SWEEP>/train/<tag>/<stamp>_JOB_default/val_metrics/validation_output_all_epochs.csv`：
  该层的逐样本评估指标（fit 后那次 holdout 跑完即写）
- `<SWEEP>/<tag>.run_summary.json`：`<name>.step<N>.run_summary.json`（注意带 step 后缀！）
- `<SWEEP>/<tag>.nmf_replacements.json`、`<SWEEP>/<tag>.exit_code`

**只有在 `JOBS` 循环全部结束后**才写 sweep 级汇总：`comparison_table.md/csv`
→ `summarize_nmf_zkp_pdb_sweep.py`（`paper_summary.*` / `paper_paired_deltas.csv`）
→ `plot_nmf_zkp_pdb_metrics.py`（`figures/`、`paper_metrics.*`）
→ 本轮新增的 `summarize_nmf_zkp_cost.py`。**中途 kill 就没有这些汇总文件。**

## 新增：跑不完也能出论文级数据（`report_partial_sweep.py`）

**背景**：sweep 级汇总只在 `JOBS` 循环全部结束后写，所以"每族只跑完一层就终止"
的话一个报告都没有。用户 2026-09-26 就是这个处境。

**新脚本**：`models/rfd3/scripts/report_partial_sweep.py`

```bash
python models/rfd3/scripts/report_partial_sweep.py --out OUT_DIR \
  [--discover /backup01/zzj/logs/train_nmf_zkp_pdb] [SWEEP_DIR ...]
```

- **就地读取**，不拷贝（GB 级 `val_structures/` 完全不碰）。
- 同名 tag 在多目录时：**有 validation CSV 的压过没有的**，打平取命令行靠前者；
  决策记进报告的 "Source-dir resolution notes"。
- 逐 tag 分档：`complete`（有 val CSV + run_summary）/ `training-only (killed before
  holdout)` / `trained N epochs, holdout missing`（跑满 schedule 但没跑 holdout）/
  `no-artifacts`。**绝不给被 kill 的 job 编 holdout 数字**（trainer 只在 fit 之后验证一次，
  且本 sweep 关了周期性验证）。
- 耗时来源：`run_summary.json` 优先，缺失时**回退解析 `<tag>.run.log` 里的
  `Epoch N Summary` 表**（rich 框线，regex 容忍 `│` 和跨行换行）→ `wall_time_source`
  标明来源。这是被 kill 的 job 唯一的耗时来源。
- 产物：`partial_report.md`（含状态表 / 族覆盖率 / holdout lDDT + bootstrap CI /
  配对 delta / 训练进度与成本 / **自动草拟的英文结果段落** / 缺失清单）、
  `partial_summary.csv`、`partial_paired_deltas.csv`、`partial_per_example_lddt.csv`、
  `partial_status.json`、4 张图（holdout lDDT 含逐样本散点与 CI、配对 delta、
  epochs 进度、训练曲线）。
- **数值口径与官方一致**：直接 import `summarize_nmf_zkp_pdb_sweep`（lDDT/bootstrap）
  与 `plot_nmf_zkp_pdb_metrics`（曲线键名），实测与 `paper_summary.csv`
