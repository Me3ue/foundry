# 2026-09-27

## 故障：跑 600+ epoch 后 `/tmp` 被占满，DataLoader 送不出 batch

**现象**（用户日志）：训练到 `Epoch 607/699`，开始每 ~2 秒刷一次
```
multiprocessing/queues.py _feed -> _ForkingPickler.dumps -> torch/.../reductions.py reduce_storage
 -> DupFd -> resource_sharer.register -> Listener -> tempfile.mkdtemp('pymp-')
OSError: [Errno 28] No space left on device: '/tmp/pymp-xxxx'
```
伴随 atomworks 的 ccd/rdkit warning，然后 `Starting epoch 608/699` 继续。

**根因（已核实代码路径）**：Linux 上 torch 默认共享策略是 `file_descriptor`
（`torch/multiprocessing/__init__.py:54`），CPU tensor 跨进程靠
`reduce_storage` → `storage._share_fd_cpu_()` → `DupFd(fd)` 传 fd；
`resource_sharer` 需要在一个 unix socket 上做，socket 位于
`TMPDIR/pymp-XXXX/listener-*`（`multiprocessing/util.py:get_temp_dir()` 用
`tempfile.mkdtemp(prefix='pymp-')`，只 **每个进程建一次**，靠 **atexit** 删除）。
DataLoader worker **每个 epoch 重建、且被信号杀死** → atexit 不执行 →
**每个 worker 每 epoch 泄漏一个目录**。700 epoch × 8 workers ≈ 5600 个目录，
tmpfs 上每个目录至少占一页 → 小 `/tmp` 必满。

**为什么 epoch 还在推进**：`dataloader/default.yaml` 里训练集有
`n_fallback_retries: 4`，所以个别样本/批次失败会被重试，不至于立刻整体崩。
但 `_feed` 线程抛异常后**会退出**，那条 queue 之后再也送不出数据 → 主进程可能
永久阻塞在 `next(iter(loader))`。所以"日志还在动"≠"还能跑完"。

**修复（已提交 `8a67b6a`）**：

1. `run_nmf_zkp_pdb_sweep.sh` 默认 `export TMPDIR=${LOG_ROOT}/_worker_tmp`
   （大磁盘；`LOG_ROOT` 在 `/backup01`），并在可用空间 <2 GiB 时前置告警。
   验证：子进程 `env` 里确实带上了 TMPDIR。
2. `PERSISTENT_WORKERS=1` → `dataloader.train.dataloader_params.persistent_workers=true`。
   **这个真能堵住泄漏**：`fabric.fit()` 只接收一个 DataLoader 对象，
   `train_loop` 的 `while not self.should_stop` 循环复用同一个 loader
   （只是 `train_loader._num_iter_calls = current_epoch` 控制重采样），
   所以 worker 不会每 epoch 重生。
3. 新脚本 `models/rfd3/scripts/cleanup_worker_tmp.sh`：**默认 dry-run**，
   `--keep N` 保留最新 N 个目录（= 当前 epoch 的 worker，删掉会把活着的
   worker 的 socket 路径抹掉）、`--min-age`、`--top`、`--apply` 才真删；
   对 `/`、`/home`、`$HOME`、`/usr`、`/etc`、`/backup01` 等有硬护栏。

**给用户的救活顺序**：先判断进程是否还活着（epoch 约 33 min，
`Finished epoch` 超过 ~35 min 没动就是卡死）→ `df -h /tmp` 判断是否 tmpfs →
tmpfs 就 `sudo mount -o remount,size=8G /tmp`（立即生效、不破坏现有文件与 socket）
→ 否则跑清理脚本 → 看 `tail -f` 是否继续出 `Finished epoch`。
**被 kill 的 feeder 线程无法复活**；且 `save_checkpoints=false` 意味着没有断点，
重启 = 从头再来，所以能救就别重启。

**教训**：这个仓库的 sweep 是"长跑 + 每 epoch 重建 worker + 小 tmpfs"的组合，
下次长跑前先 `df -h` 看 `/tmp`，并开 `PERSISTENT_WORKERS=1`。

## 服务器 `git pull` 被本地未提交改动挡住（已演练并给出流程）

**服务器状态**（`/backup01/zzj/protein/foundry`）：HEAD 还停在 `2ee405f`，工作区有 6 个文件
被**手工打过我给的补丁**（未提交），另有未跟踪的 `fix_nmf_zkp_eval_errors.patch` → `git pull`
报 "Your local changes would be overwritten" + "untracked working tree files would be overwritten"。

**远端多出来的那个提交**：`1a8f13d new`（用户自己提交的，内容只是把
`fix_nmf_zkp_eval_errors.patch`（498 行）加进仓库）——正是它导致"未跟踪文件会被覆盖"那条报错。

**放行流程（沙箱 1:1 复现 + 端到端验证通过）**：

```bash
git diff > ~/server_local_changes_$(date +%F_%H%M).patch   # 留档
git stash push -u -m server-preMerge                        # -u 必须带（未跟踪文件）
git status --short                                          # 应为空
git pull origin main                                        # Fast-forward
bash models/rfd3/scripts/verify_nmf_zkp_fixes.sh            # 11/11
```

**关键点**：stash 里存的就是 `dc2d7cd` 的内容，而仓库里已经有它（甚至更新，例如
`run_nmf_zkp_pdb_sweep.sh` 后来还加了 TMPDIR 修复）→ **绝对不要 `git stash pop`**（会把新修复
倒退回去）。核对 `git stash show --stat` + 自检 11/11 后 `git stash drop` 即可。

**远端那个 `1a8f13d` 建议清掉**（冗余的 498 行补丁文件，且会持续干扰未跟踪检查）：
`git rm fix_nmf_zkp_eval_errors.patch && git commit -m "chore: drop redundant patch" && git push`。

**教训**：以后别再发 `.patch` 让用户手工打 —— 直接 commit + push + 那边 pull。
