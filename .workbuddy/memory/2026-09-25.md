### 实测得到的“不是 bug 但要知道”的事实

- `t = 16·exp(-1.2+1.5·N(0,1))`（sigma_data=16）→ 范围约 0–80；序列损失 `max_t=1`
  所以**只有 t<1（约 14.7% 的样本）**才产生序列损失，`train/per_epoch_seq_recovery`
  只在那些 batch 出现 → 小样本 smoke 跑里这列经常是空的/0。这是上游设计。
- lDDT 对**刚体变换天然不变**（我第一版审计误判成“不敏感”，因为平移不改变原子间距离）。
- `EMA.decay=0.999` 对短跑是灾难：572 步时 shadow 只走了 ~43% 的训练进程，
  而验证用的正是 shadow（`EMA.forward` 在 eval 模式转发到 shadow）。
  变体间对比仍自洽，但绝对 lDDT 被低估。想改就调 `model.ema.decay`（如 0.99）。
- `EMA.shadow` 的参数经 `detach_()` 后 `requires_grad=False`（实测）→ **不会**污染
  trainable 计数；只有 `parameters()` 总数会翻倍（即上表 #4）。
- `ReplacementNMFLinear` 把符号锁死（`weight_sign` 是 buffer，U/M/V 非负）→
  `sign(W_nmf)==sign(W_base)` 恒成立（实测 1.000），只能调 magnitudes。随机权重下
  rank-8 初始化的相对 Frobenius 误差约 0.51–0.60 → NMF 变体在 step 0 就与 baseline
  不等价，比较时要注意这个起跑线差异。
- `parameter_freezing_config` 缺省 = 不冻结（`freeze_by_default=False`）；
  完全冻结的模型 loss 没有 grad_fn，会在 `backward()` 崩 → 只能配零训练步使用。
- `is_original_unindexed_token` 的**层级两处定义不一致**：`conditioning_base.py:524` 存的是
  原子级（`apply_and_spread_token_wise` + 拼接扩展原子），`util_transforms.py:189` 注释写
  `[n_tokens]`，而 loss 里当 token 级用（`[tok_idx]` 索引）。只在 unindexed motif 训练时
  才有非零值（本 sweep 恒为全 False，`torch.any` 直接跳过分支），所以**没动它**——
  真要修得先确定作者意图。同类：`trainer/rfd3.py:336` 的 `# [D, L]` 注释也是错的
  （`mask_atom_lvl` 实际是 1D `[L]`）；`seq_token_lvl` 注释写 `[I,32]` 实际是 `[I]`。
- 周期性验证 `should_validate = current_epoch % validate_every_n_epochs == 0`；
  `recycle_schedule` 在构造时按 `(max_epochs, n_examples_per_epoch)` 生成，与
  `assemble_distributed_loader(n_examples_per_epoch=...)` 的 sampler 长度一致 → 无越界风险。

## 补充（同日第四轮）：48G A6000 上的训练参数调优（LAYER_SET=all）

用户机器是 **6× A6000 48GB + 32 逻辑核 + 503GB 内存**（不是早前笔记里的 11.5GiB 卡），
问默认参数是否太保守。核实后的事实：

- **真正生效的裁剪限制是 `max_atoms_in_crop`**：atomworks 的 crop 先按 `crop_size` 选 token，
  再用 `resize_crop_info_if_too_many_atoms(max_atoms=...)` 裁回原子预算
  （`atomworks/ml/transforms/crop.py:413`）。所以 `CROP_SIZE=256` + `MAX_ATOMS=1920`
  实际只有 **~137 残基**（token 按 atom14 最多 14 原子）。要真用 256 残基需 `MAX_ATOMS≈3584`。
  上游预训练口径是 `crop_size=384 / max_atoms_in_crop=3840`（≈274 残基，同样被原子预算卡住）。
- **验证阶段硬编码 `diffusion_batch_size: 1`**（`configs/datasets/val/pdb_holdout.yaml:57`）
  → 提高 `DIFFUSION_BS` 只影响训练显存，不会让 holdout 评估 OOM ✓。
- 训练 pipeline 的 D 来自 `datasets.diffusion_batch_size_train`
  （`train/pdb/base_transform_args.yaml:16` → `BatchStructuresForDiffusionNoising` +
  `SampleEDMNoise`），即**每个结构 D 个噪声样本**。
- 显存模型：主项是原子对张量 → **峰值 ∝ D · L²**。以旧默认 (D=4, L=1920 → 14.7M) 为 1 单位：
  D=16/L=1920 → 4×；D=16/L=2560 → 7×。
- 耗时模型：`MAX_EPOCHS × N_EXAMPLES`（每结构一次前向）+ 每个 epoch 的固定主机开销
  （载入/裁剪/特征化）。提高 D 不减少 step 数，但摊薄主机开销 → 可**按 ~2×（而非 D 倍）**
  下调 `MAX_EPOCHS`（同一结构的噪声样本相关）。
- 实测耗时只能看 `<sweep>/<tag>.run.log` 里 train_logging 打的
  “Mean Time per Batch (s) / Elapsed Time (s)”表格（**没有**进 metrics.csv）。

**产物**：sweep 脚本新增 `PRESET`（显式 env 优先）：
`PRESET=small`(旧默认) / `a6000`(D=16, 8 workers, PF=4) / `a6000xl`(D=16 + MAX_ATOMS=2560)。
用 stub python 端到端验证过参数确实传进 hydra（`diffusion_batch_size_train=16` 等）。
脚本头部还写了多卡并行配方：**拆 LAYER_SET + 共享 SWEEP_DIR，baseline 只在一个进程里跑**，
最后手动跑 `summarize_nmf_zkp_pdb_sweep.py` + `plot_nmf_zkp_pdb_metrics.py` 出总报告。

**提醒用户的科学风险（重申）**：`LAYER_SET=all` = 6 encoder + 6 proj + 2 head = 14 个 NMF job
（各 ~6k 可训练参数）+ baseline；而 baseline 无任何冻结 → 是 **168M 参数全量微调**。
一旦为了省时间砍 epochs，受损最重的是 baseline（远未收敛）→ 结论会系统性偏向 NMF。

**两个实现坑（已处理，值得记住）**：
1. **别用软链接合并**：Python 3.13 起 `pathlib.rglob` 默认 `recurse_symlinks=False`，
   `plot_nmf_zkp_pdb_metrics.py` 的 `sweep_dir.rglob("metrics.csv")` 会漏掉符号链接目录。
   用 `cp` 复制（这几个文件才几百 KB）。
2. `cp -rl`（硬链接）做目录合并会撞 “are the same file” 报错，且 `cp -r src/train $M/`
   在 `$M/train` 已存在时会嵌套成 `$M/train/train`。正确写法是
   `find ... | cp --parents -t $M/train/`，或逐文件判存在后复制（脚本里用后者实现“先到先得”）。
   另外沙箱有**批量删除保护**：`rm -rf` 一个含 >50 文件的目录会被 safe-delete 钩子拦下，
   换个新目录名而不是删旧目录。

`INCLUDE_BASELINE=1` 只在一个进程里开，最后手动重跑 `summarize_nmf_zkp_pdb_sweep.py` +
`plot_nmf_zkp_pdb_metrics.py`（各进程结束时都会重写 `comparison_table.md`，只覆盖当时的 job）。
